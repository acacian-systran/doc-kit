# 그림 문법

**모양이 저장소의 종류를, 색이 역할을 말한다.** 라벨을 읽기 전에 구조가 먼저 보이게
하려는 것이다. 정의는 `_style.d2` 한 벌뿐이고 각 그림이 `...@_style` 로 임포트한다 —
그림 파일에 색상값을 직접 적지 않는다.

`_` 로 시작하는 파일은 그림이 아니라 자재다. 관점을 가리지 않는 자재(`_style.d2`,
`_template.d2`)는 그림보다 한 층 위에 두고 `...@../_style` 로 임포트한다.

## 상자

| 클래스 | 보이는 것 | 뜻 |
|---|---|---|
| `외부` | 회색 점선 | 우리가 만들지 않은 것 — 외부 API · 남의 모듈 |
| `트리거` | 노랑 육각형 | 무엇이 그 실행을 부르나 — cron · 사람 · HTTP 요청. 우리 코드 안이 아니다 |
| `단계` | 파랑 상자 | 무언가를 하는 곳 |
| `필터` | 청록 상자 | **거르는** 단계와 조건 게이트 — 여기서 대상이 줄어든다 |
| `파일` | 노랑 문서 | 파일시스템 |
| `테이블` | 회색 실린더 | RDB — 행을 보관하는 곳 |
| `정본` | 회색 실린더 + **굵은 테두리** | 같은 DB 지만 잃으면 복구가 어렵거나 비싼 것 |
| `색인` | 보라 실린더 | 같은 DB 안의 인덱스 — 검색을 받는 곳 |
| `비결정` | 붉은 상자 | LLM 이 닿는 것. 결과가 매번 같지 않다 |
| `조회` | 초록 상자 | 쓰기가 하나도 없는 것 |
| `영역` | 회색 점선 컨테이너 | 소유 경계 |
| `열이름` · `행이름` | 테두리 없는 글자 | 격자의 좌표축 이름. 그림이 아니라 축이다 — 열이 시간이거나 행이 계층인 격자에서만 쓴다 |
| `빈칸` | 아무것도 안 보임 | 격자에서 비는 칸. 자리는 차지한다 |

**정본의 모양은 정본이 있는 곳을 따라간다.** 파일시스템에 있으면 `page`, DB 로 이관하면
`cylinder` 다. 모양은 저장소의 종류를 말하는 자리이고, 굵은 테두리의 뜻("잃으면 복구가
어렵거나 비싸다")만 그대로다.

## 선

화살표 색이 그림 파일에 인라인으로 박히면 같은 뜻이 파일마다 갈라진다. 선에도 클래스를
쓴다.

| 클래스 | 보이는 것 | 뜻 |
|---|---|---|
| `축` | 굵은 검정 | 축. 이것만 따라가면 전체가 읽힌다 |
| `부수` | 얇은 회색 | 받아오는 것, 남기는 것 |
| `읽기` | 초록 점선 | 읽기만 하는 흐름 |
| `호출` | 붉은 선 | 비결정으로 나가는 흐름 |

그 밖에 **점선 테두리는 아직 없는 것**을 뜻한다.

## 배치

**3열 격자가 기본형이다.** 왼쪽은 바깥에서 받는 것, 가운데는 단계, 오른쪽은 그 단계가
남기는 것. 열이 곧 의미라서 화살표가 교차하지 않고, 빈 칸은 `빈칸` 클래스로 자리만
채운다(비우면 격자가 밀린다).

**열의 뜻은 그림마다 다시 정할 수 있다.** 남기는 것이 없는 조회 모듈이라면
`왼쪽 = 어디서 읽나 · 가운데 = 단계 · 오른쪽 = 응답에 실리는 것`이 맞다. 그때는 굵은
축의 뜻도 파이프라인이 아니라 요청 하나가 지나가는 길이다. 뜻을 바꿨으면 머리말과
"읽는 법"에 적는다.

**시간을 그려야 하면 격자를 눕힌다** — 열을 시간, 행을 "어디에 있나"로 둔다. 자유
배치로 그리면 시간 축이 layout 엔진 손에 넘어간다.

**행 순서로 화살표를 다스린다.** 오가는 상대를 인접 행에 두면 화살표가 중간 행의 상자를
관통하지 않는다. 산출물을 맨 아래 한 행에 몰면 위쪽 단계에서 나온 선이 아래 단계를
관통한다 — `적재 → 창 계산 → 분석 → 결과` 처럼 펴서 모든 화살표를 인접 행 사이에 가둔다.
**고치고 나면 대개 사실에도 더 가깝다** (분석은 적재 프로세스가 아니라 적재가 남긴 것을
읽는다). 관통하는 화살표는 대개 배치 문제가 아니라 그림이 인과를 건너뛰었다는 신호다.

**눕힌 격자라고 굵은 축이 가로로 흐르는 것은 아니다.** 열이 이어지는 흐름이 아니라 겹쳐
도는 두 체제라면 열 사이에 화살표를 두지 않는다 — 가로로 이으면 왼쪽이 끝난 뒤 오른쪽이
시작되는 것처럼 읽힌다. 눕힌 격자를 그릴 때는 축의 뜻을 머리말과 "읽는 법" 양쪽에 적는다.

**한 파일에서 그림을 격리해야 하면 `layers:` 를 쓴다.** 출력이 파일 하나가 아니라
디렉터리가 된다(`<이름>/{index,<레이어>}.svg`). 한 장만 뽑으려면 `d2 --target=<레이어>`.
보드마다 노드 집합이 같으면 `_<이름>-nodes.d2` 를 한 벌 두고 여럿이 임포트한다. 노드
집합이 다르면 공유 자재를 두지 않는다. **같은 라벨이 두 보드에 적히기 시작하면** 한쪽만
고쳤을 때 갈라진다 — 눈에 보이기 시작하는 시점에 공유 자재로 뺀다.

## 무엇을 그리지 않나

**설명은 상자 안에 넣는다.** 선 위의 라벨은 글자가 선과 겹치고, 조건을 괄호로 묶으면
조건인지 부연인지 구분되지 않는다. 조건은 자기 칸을 갖고 `필터` 색을 입는다.

**판단의 근거는 `.d2` 주석에 남긴다.** 왜 이 게이트를 두지 않았는지, 왜 이 순서인지는
그림에 그리지 않는다 — 대신 근거 문서의 파일명과 절 번호를 주석으로 적는다.

**관점 그림은 모듈이 가진 것을 다시 그리지 않는다.** 관점 그림은 여러 모듈을 한 장에
담고, 모듈 그림은 한 모듈을 깊게 판다. 관점 그림에서 남의 모듈 행은 그 모듈이 무슨
단계를 지나는지가 아니라 이 관점이 묻는 것만 답한다 — 단계는 모듈 그림에 있다.

**같은 사실이 두 그림에 있으면 한쪽이 낡는다.** 남는 것이 그림 한 장을 유지할 값이
안 되면 지운다. 지운 근거와 숫자는 커밋 이력과 spec 에 남는다.

## 그림을 언제 나누나

한 그림은 질문 하나에 답한다. 답하는 질문이 둘이면 그림을 둘로 나눈다.

**"한 대상이 지나가는 순서"와 "한 실행이 도는 순서"가 다르면 반드시 나눈다.** 둘이 같은
모듈은 한 장으로 끝나지만, 비동기 대기(제출과 회수 사이 24시간 같은 것)가 끼면 한
프로세스가 대상을 끝까지 들고 있을 수 없어 둘이 갈라진다. 한 장에 그리면 굵은 축이
"대상이 이 순서로 지나간다"로 읽히는데 그것이 거짓이다.

**중복도 나누는 근거다.** 한 보드의 칸 절반이 다른 축(예: 배치 기계장치)에 속하고 그것이
이미 다른 보드에 있다면, 남은 질문("무엇을 근거로 판단하나")을 읽으려면 그 어휘를 계속
건너뛰어야 한다. 걷어낸 보드를 따로 두면 그제야 판정의 입력이 무엇인지 보인다.

**같은 세 보드에서 굵은 축의 뜻이 셋 다 다를 수 있다** — 실행 순서 · 논리 순서 · 실행
경계를 넘는 길. 관점이 다르면 같은 사실도 다른 어휘로 적는다. 이것이 보드를 나눈 값이다.

**번호는 실행의 산물이다.** 실행 순서를 묻지 않는 보드에서는 단계 번호를 뗀다. 번호를
남기면 축을 따라 `4 → 5 → 3 → 6` 같은 것이 나오고, 사실은 맞아도 첫 독자가 오타로 읽는다.
읽는 법에 "오타가 아니다"를 적어야 방어되는 그림은 이 문법의 전제(라벨을 읽기 전에 구조가
먼저 보이게)를 넘지 못한다. 대신 노드 이름을 번호 있는 보드와 맞춰 두면 대응은 남는다.

**번호를 다시 매길 때 빈자리를 남기지 않는다.** 빈 번호가 있으면 읽는 사람이 "빠진 단계가
있나"를 묻는다.

## 대형 그림

상자가 스무 개를 넘고 배포 경계가 여럿이면 격자로는 안 된다. `_template-container.d2`
를 쓴다. 아래는 그 형태에서만 생기는 규칙이다.

**최상위 한 겹만 격자로 잡고 나머지는 컨테이너로 간다.** 열 컨테이너(테두리도 배경도
없는 빈 상자)에 각 묶음을 넣으면 열이 고정되고, 격자 칸 안의 컨테이너는 자기 레이아웃을
따로 쓴다. 최상위 격자를 빼고 자유 배치에 맡기면 열이 layout 엔진 손에 넘어간다 — 실제로
넘어가 보면 제일 위여야 할 클라이언트 상자가 오른쪽 아래로 간다.

**엔진은 `elk` 를 쓴다** (`d2 --layout=elk`). 기본 dagre 는 컨테이너 간격이 헐렁해 큰
그림이 더 커진다.

**왕복은 한 선으로 합친다.** `a -> b` 와 `b -> a` 를 따로 그리면 되돌아가는 선이 배치를
끌어당긴다. `a <-> b` 로 두고 라벨에 오가는 것을 적는다.

**부연은 설명하는 컨테이너 안에 넣는다.** elk 는 `near` 에 상수만 받아 `near: <노드>` 로
각주를 붙일 수 없다. 안에 넣으면 테두리가 각주와 대상을 묶어 주므로 결과도 더 낫다.
컨테이너가 없는 것(사람 등)은 투명 그룹으로 한 겹 싸면 된다.

**범례와 꼬리말은 `near: bottom-left` · `near: bottom-right` 로 고정한다.** 고정하지
않으면 레이아웃 엔진이 그림 한복판에 놓는다.

**`left` · `right` · `center` 는 d2 예약어다.** 열 이름으로 쓰면 컴파일되지 않는다.

**열을 넘는 선은 긴 대각선이 된다.** 뜻이 다른 색이라 읽히기는 하지만 수가 늘면 그림을
덮는다. 손으로 그린 그림처럼 피할 방법은 없으므로, 열 배치를 바꿔 줄일 수 있는지 먼저
본다. 줄지 않으면 그것이 그림이 아니라 시스템의 성질이다.

### 큰 그림에서는 각주 규칙이 뒤집힌다

작은 그림에서는 부연을 `.d2` 주석에 둔다(위 "무엇을 그리지 않나"). 큰 그림에서는 그리는
쪽이 맞다. 판단 기준은 **읽는 사람이 그 사실을 모르면 그림을 오해하는가**다.

- 그린다: `As-Is: FakeGraphStore — 커도 빈 결과다` · `박스가 갈린 것은 논리 구분이지
  배포가 아니다` — 그림이 말하는 것과 실제가 다른 지점. 주석에 두면 아무도 안 본다.
- 주석에 둔다: 왜 이 순서인지, 왜 저 게이트를 두지 않았는지 — 그림을 오해하게 만들지
  않는 배경.

각주는 `각주`(회색) 또는 `경고각주`(붉은색) 클래스를 쓴다. 상자가 아니므로 테두리도
배경도 없다.

### 목표 구조와 미착륙

목표 구조(to-be)를 그리면서 **코드에 아직 없는 것**을 표시할 때 `미착륙`(빨강 점선)을
쓴다. 세 가지를 함께 지킨다.

1. **기준 시점을 제목에 적는다** — "빨강 점선 = 미착륙(2026-08-04 코드 대조)". 시점이
   없으면 언제 낡았는지 알 수 없어 아무도 그 표시를 못 걷는다.
2. **표시가 없는 것은 코드와 일치한다고 선언한다.** 꼬리말에 적는다. 이 문장이 없으면
   미착륙 표시가 "여기는 확인했다"인지 "여기만 확인했다"인지 알 수 없다.
3. **어긋났을 때 어느 쪽이 이기는지 적는다.** to-be 규약이라면 그림이 이긴다 — 코드가
   밀린 것이지 그림이 틀린 것이 아니다.

붉은색은 미착륙이 독점한다. `비결정`(LLM 이 닿는 것)이 주황으로 옮긴 것이 그래서다 —
아직 없는 것은 그림 어디에 있든 눈에 띄어야 하고, 경고색은 그쪽이 더 필요하다. 옮기고
나니 `모델` 선과 한 가족이 되어 모델이 닿는 상자와 모델을 부르는 선이 같은 색이 됐다.

### 컨테이너 두 종류

`영역`(점선)은 논리 그룹, `배포`(실선)는 배포 경계다. 큰 그림에서 이 둘은 다른 질문에
답한다 — **"같이 묶여 있나"와 "같이 죽나"는 같은 말이 아니다.** 배포 경계를 점선으로
그리면 "이 안은 한 번에 내려간다"를 말할 수단이 없어진다.
