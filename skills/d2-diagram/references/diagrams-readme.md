# 그림 디렉터리의 README

그림만 두면 반드시 낡는다. 낡은 그림은 없는 것보다 나쁘다 — 읽는 사람이 틀린 것을 믿게
된다. README 가 막는 것은 낡음 자체가 아니라 **낡았을 때 어느 쪽이 틀린 것인지 모르는
상태**다.

## 목표 상태로 둘 것인가, 현재 상태로 둘 것인가

먼저 정하고 README 첫 줄에 적는다. 둘을 섞으면 그림이 코드와 어긋났을 때 무엇을 고쳐야
할지 정할 수 없다.

**목표 상태(to-be)로 둔다면** 갱신 의무를 두지 않는다. 코드가 앞서 나가면 그림이 틀린
것이 아니라, 그림이 목표였고 코드가 거기 도달한 것이다. 대신 **현재 상태의 정본이
어디인지**를 적는다(코드와 마이그레이션 디렉터리 등).

이 규약에는 대가가 따른다. 코드를 정본으로 삼아 그림을 뒤집고 싶어지는 순간이 오는데,
그것이 규약 위반이다 — 어긋남의 방향을 정하는 것은 코드가 아니라 설계자다. 어긋난 것이
그림인지 코드인지는 사람이 판단해 커밋 메시지에 남긴다.

**현재 상태(as-is)로 둔다면** 무엇이 바뀔 때 그림도 고치는지를 적는다. 의무를 지킬 수
없다면 그 그림은 애초에 그리지 않는 편이 낫다.

## 무엇을 적나

**답하는 질문 표.** 파일마다 한 줄. 그림을 찾는 사람은 파일 이름이 아니라 질문으로
찾는다.

```markdown
| 파일 | 답하는 질문 |
|---|---|
| `<이름>-overview.d2` | 모듈이 몇이고 경계가 어디인가 |
| `<이름>-infra.d2`    | 무엇이 언제 돌고 상태가 어디에 남나 |
```

**왜 나눴는지.** 경계와 런타임을 한 장에 섞으면 스키마·파일과 프로세스·롤이 같은 평면에
앉아 두 질문 중 어느 것도 답하지 못한다 — 이런 판단을 적어 두지 않으면 다음 사람이
"합치면 되지 않나"로 되돌린다.

**열과 축의 뜻이 기본형과 다른 그림.** 기본형은 `왼쪽 = 받는 것 · 가운데 = 단계 ·
오른쪽 = 남기는 것`이다. 다르게 쓴 그림은 그 뜻과 이유를 적는다.

**읽는 법.** 보드가 여럿이면 보드마다 굵은 축이 무엇을 뜻하는지. 점선처럼 뜻이 붙은
표시가 있으면 그 뜻도.

**그린 시점.** 날짜와, 그 시점의 기준(마이그레이션 리비전·태그·커밋). 이후 개정은 무엇이
왜 바뀌었는지 한 줄씩 덧붙인다. 이 절이 길어지는 것은 정상이다 — 그림에 그리지 않기로 한
근거가 전부 여기로 오기 때문이고, 그 근거야말로 다음 사람이 필요로 하는 것이다.

**렌더 명령.** 복사해서 바로 돌릴 수 있는 형태로.

## 렌더

```bash
cd <디렉터리>
for f in <이름1> <이름2>; do d2 $f.d2 $f.svg; done
```

`layers:` 가 있는 파일은 출력이 디렉터리다(`<이름>/{index,<레이어>}.svg`). 위 루프의
마지막 인자는 그대로 둬도 `d2` 가 디렉터리로 알아서 쓴다. 한 장만 뽑으려면
`d2 --target=<레이어> <이름>.d2 <레이어>.svg`.

**`.svg` 를 함께 커밋한다** — `d2` 없이도 보이게 하기 위해서다. `.d2` 를 고치면 같은
커밋에서 `.svg` 도 다시 뽑는다.

PNG 출력(`d2 ... out.png`)은 Playwright 드라이버를 내려받는다. 그 다운로드가 막힌
환경이면 SVG 를 쓴다.
