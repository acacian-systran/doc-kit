# build — 환경과 성질 검사

사다리 1~3칸. 산출은 `env.md` · `decisions.md` · `src/` · `tests/` 다.

---

## 1. 환경

`papers/<citekey>/lab/` 에서 독립 프로젝트로 구축한다. 호스트 프로젝트의 의존성 파일을
수정하지 않는다.

```bash
cd papers/<citekey>/lab
uv init --no-workspace          # 호스트 프로젝트의 workspace 에 편입되지 않게
uv add <논문이 요구하는 패키지>
uv lock
```

`--no-workspace` 를 빠뜨리면 호스트의 `pyproject.toml` 이 수정된다.

**`env.md` 템플릿.**

```markdown
# 환경

| 항목 | 값 |
|---|---|
| 기록일 | YYYY-MM-DD |
| OS·장치 | |
| Python | |
| 핵심 패키지 | <논문 결과에 영향을 주는 것만. 전체는 uv.lock> |
| 모델·API | <모델 id, 버전, endpoint> |
| 데이터 출처 | <URL 과 내려받은 날짜. 분할 파일의 해시> |
| 시드 | |
| 논문의 환경 | <논문이 기재한 것. 미기재면 `미보고`> |

## 논문 환경과의 차이

| 항목 | 논문 | 내 환경 | 결과에 영향 |
|---|---|---|---|
```

마지막 표가 `gap` 의 입력이다. 차이를 미리 적어 두면 격차가 발생했을 때 처음부터 다시
조사하지 않는다.

**시드를 한 곳에서 고정한다.** 프레임워크마다 난수원이 여러 개이므로 `src/seed.py` 같은
단일 지점을 두고 `run.py` 가 전달한 값을 받는다. 데이터 순서·초기화·드롭아웃·평가 표집이
모두 그 한 값에서 도출되어야 재현이 성립한다.

## 2. `decisions.md` — 이 모드의 본체

### 결정의 판별법

구현 중 어떤 값이나 순서를 정할 때 **논문에서 그것을 지시하는 문장을 찾을 수 없으면
결정이다.** 세 부류가 있다.

| 부류 | 예 |
|---|---|
| 미기재 | 초기화 방식, 절단 상한, 후보 정렬 순서, 재시도 횟수 |
| 모호 | "수백 개", "적절히 표집", "몇 개의 예시" |
| 충돌 | 본문과 부록의 설정이 어긋난다. 어느 쪽을 따랐는지가 결정이다 |

**코드 주석에 남기지 않는다.** `grep` 대상이 분산되면 `gap` 의 용의자 명단이 성립하지
않는다. 코드에는 `# D3` 처럼 항목 번호만 참조한다.

### 항목 형식

```markdown
### D<번호> · <한 줄 제목>
- 정한 것: <무엇을 어떻게>
- 근거: <왜 그렇게. 논문 밖 근거면 그렇다고 기재>
- 논문의 공백: <논문 어디가 어떻게 비어 있나. 앵커>
- 민감도: <바꾸면 무엇이 달라질 것 같나. 높음/중간/낮음 + 한 줄>
```

`민감도` 가 `gap` 의 3순위 용의자 정렬 기준이다. 비워 두면 격차가 발생했을 때 전체 항목을
다시 읽게 된다.

### 예시 셋

```markdown
### D1 · 컨트롤러 온도
- 정한 것: temperature 1.0, top-p 0.9
- 근거: 본문과 부록이 어긋날 때 실제 호출 설정이 기재된 부록을 따랐다
- 논문의 공백: 본문은 greedy·temperature 0 으로 deterministic 을 주장하고
  (§Implementation Details, p.6), 부록의 컨트롤러 호출은 temperature 1.0·top-p 0.9 다
  (§F.2, p.16)
- 민감도: 높음 — 확률적이면 표의 모든 수치가 단일 실행값이 아니다. 3시드 필수

### D3 · lookup 후보 절단 상한
- 정한 것: 원시 이웃을 200개로 절단한 뒤 Eq. 3 의 필터를 적용
- 근거: 컨텍스트 한계. 절단을 필터 앞에 둔 것은 비용 때문이며 논문 근거는 없다
- 논문의 공백: 큰 개체가 "수백 개" 를 노출한다고만 기재하고 상한·순서·기준 모두 미기재
  (§Problem Setup, p.4)
- 민감도: 높음 — 상한이 낮으면 정답 속성 잔존율이 Table 9 (p.10) 의 62.1% 보다 낮아진다.
  절단을 필터 뒤로 옮기면 값이 달라진다

### D7 · 답 type 추론 실패 처리
- 정한 것: JSON 파싱이 실패하면 answer_type 을 비우고 진행
- 근거: 임의 결정. 재시도와 비교하지 않았다
- 논문의 공백: 프롬프트는 두 필드의 JSON 을 요구하나 (§F.1, p.15) 파싱 실패 처리는 미기재
- 민감도: 낮음 — answer_type 은 안내로만 쓰이고 속성을 버리는 데 쓰이지 않는다
  (§Schema Index and Type State, p.4)
```

### 개수의 감각

10개 미만이면 결정을 코드에 숨겼을 가능성이 높다. 논문 한 편을 실제로 구현하면 미기재
항목이 그보다 많이 도출된다. `grep -rn "TODO\|FIXME\|hardcode\|magic\|임의" src/` 로 훑고
남은 것을 항목으로 올린다.

내 구현이 같은 순서로 밟는지가 가장 값싼 검증이다.

**C형 · 시스템·커널**

1칸이 정확성 동치 검사(기존 구현과 같은 입력에서 수치 허용오차 안의 같은 출력). 2칸 이후는
측정 방법론이 본체다 — 워밍업 제외, 반복 횟수 고정, 분산 보고, 측정 대상 외 비용 분리.
속도 주장은 측정 절차가 곧 결과이므로 `decisions.md` 에 측정 절차를 항목으로 올린다.

**D형 · 이론**

구현이 아니라 수치 검증이다. 정리의 가정을 코드로 옮기고 경계값과 가정 위반 입력에서
결론이 성립하는지 확인한다. 반례 탐색이 5칸에 대응한다.

## 4. 성질 검사 카탈로그

수식이 함의하는 불변량을 코드로 옮긴다. 학습 없이, 초 단위로 돌아야 한다.

**공통**

- 결정성 — 같은 시드·같은 입력에서 두 번 실행한 결과가 일치한다
- 형상·dtype — 논문의 식이 지시한 차원과 일치한다
- 경계 입력 — 길이 1, 빈 집합, 최대 길이에서 예외 없이 동작한다
- 시드 반응 — 시드를 바꾸면 결과가 달라진다. 달라지지 않으면 시드가 연결되지 않았다

**A형**

- 정규화 — softmax 출력의 행 합이 1, 분포의 합이 1
- 마스킹 — causal 마스크에서 미래 위치의 기울기가 0. 마스크 위치를 바꾸면 출력이 변한다
- 등변성·불변성 — permutation equivariance, translation invariance 등 논문이 주장한 대칭
- 기울기 도달 — 모든 학습 파라미터에 `grad` 가 None 이 아니고 0 이 아니다
- 스케일 — 논문이 스케일 인자를 도입했으면(예: 1/√d) 제거 시 분산이 변하는 것을 확인한다
- 파라미터 수 — 논문이 기재한 값과 일치한다. 불일치는 구조 오류의 가장 빠른 신호다

**B형**

- 출력 파싱 — 생성 결과가 목표 문법으로 파싱된다
- 스키마 준수 — 생성된 식별자가 스키마에 존재한다. 존재하지 않는 것을 생성하는 비율을 잰다
- 도구 계약 — 도구가 반환한 후보 밖의 값을 컨트롤러가 선택하지 못한다
- 필터의 양방향성 — 필터가 걸러야 할 것을 걸러내고, 걸러서는 안 되는 것을 남긴다.
  통과 조건이 여러 개인 필터는 조건마다 사례를 작성한다
- 예외 경로 — 논문이 기재한 fallback 이 실제로 발동한다. 발동 조건을 인위적으로 구성한다
- 프롬프트 고정 — 프롬프트 해시가 run 간 동일하다. 프롬프트가 변하면 비교가 깨진다
- 멱등성 — 같은 상태에서 같은 도구 호출이 같은 관측을 반환한다

**C형**

- 기존 구현과의 수치 동치(허용오차 명시)
- 입력 크기를 바꿀 때 출력이 같고 시간만 변한다
- 병렬·직렬 결과 일치

**D형**

- 정리의 가정을 만족하는 입력에서 결론이 성립한다
- 가정을 위반하는 입력에서 결론이 깨진다 — 깨지지 않으면 구현이 가정을 쓰지 않는다
- 경계값·극한에서 수식이 발산하지 않는다

**논문의 예외 경로를 반드시 검사한다.** 방법 절이 "이 경우에는 건너뛴다" 고 기재한 자리가
구현에서 가장 자주 틀리고, 정상 경로만 검사하면 드러나지 않는다.

## 5. 미니 과적합

A형에서 3칸의 합격 조건이다.

1. 8~16 예제를 고정하고 정규화·드롭아웃·증강을 모두 끈다.
2. 손실이 0 근처까지 내려가는지 본다. 내려가지 않으면 학습 코드의 결함이다.
3. 실패 시 확인 순서 — 손실 함수의 축, 레이블 정렬, optimizer 에 전달된 파라미터 집합,
   학습률 규모.

**통과하지 못하면 4칸으로 오르지 않는다.** 축소 학습에서 지표가 낮게 나오면 원인이
방법인지 버그인지 구분되지 않는다.

## 6. 흔한 오판

- **성질 검사를 학습 코드 뒤로 미루는 것.** 2칸은 초 단위이고 3칸은 분 단위다. 순서를
  뒤집으면 버그 하나를 찾는 데 학습 한 번이 든다.
- **정상 경로만 검사하는 것.** 논문의 예외 처리가 구현에서 가장 자주 틀린다.
- **결정을 코드 주석으로 처리하는 것.** `decisions.md` 가 비면 `gap` 이 직감이 된다.
- **파라미터 수 확인을 건너뛰는 것.** 논문이 값을 기재했으면 가장 값싼 구조 검증이다.
- **`uv init` 에서 `--no-workspace` 를 빠뜨리는 것.** 호스트 프로젝트가 수정된다.
