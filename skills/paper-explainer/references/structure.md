# 목차와 흐름 나누기

`sections.js` 를 채우는 기준. 사용자에게 확인받는 것도 이 결과다.

## 1. 섹션 목록

논문의 Section · Subsection 을 그대로 따른다. 번호를 새로 매기지 않는다 — 원문과
번호가 같아야 해설 페이지와 논문을 나란히 놓고 읽을 수 있다.

| 경우 | 처리 |
|---|---|
| 챕터에 하위 챕터가 있다 | 챕터 페이지 1장 + 하위 챕터마다 1장. 챕터 페이지는 하위 챕터들의 지도 역할 |
| 하위 챕터가 없다 | 챕터 페이지 1장 |
| 하위 챕터 본문이 반 쪽 미만이다 | 상위 페이지에 합친다. `merged: ["3.2.1", ...]` 로 남기고 본문 소제목으로 살린다 |
| 3단계(3.2.1) 하위 챕터가 길다 | 페이지로 뺀다. id 가 `3.2.1` 이면 깊이 3 |
| Related Work | 한 페이지로 두거나, 해설할 내용이 없으면 Overview 에 한 문단으로 합친다 |
| 부록 | 본문이 부록을 참조하고 그 내용이 이해에 필요할 때만. id 는 `A`, `A.1` |
| Abstract · Acknowledgments · References | 페이지로 만들지 않는다 |

합친 것과 뺀 것은 Overview 의 `읽는 법` 에 적는다. 독자가 원문 목차와 대조할 때
사라진 섹션이 어디 갔는지 알아야 한다.

## 2. 흐름 단계 (stages)

Overview 흐름도와 미니맵의 큰 블록이다. **논문의 목차가 아니라 논증의 흐름**이다.

- 4~7개. 3개 이하는 위치 표시로 쓸 정보가 없고, 8개 이상은 미니맵에서 한눈에 안 들어온다.
- 단계 이름은 2~6자 한국어 명사. `문제` · `기존 방법의 한계` · `제안 방법` · `분석` · `실험` · `결론`.
- 논문 유형에 따라 고친다.

| 유형 | 흐름 예 |
|---|---|
| 방법 제안 | 문제 → 기존 한계 → 핵심 아이디어 → 구성 요소 → 실험 → 분석 → 결론 |
| 벤치마크·데이터셋 | 동기 → 구축 과정 → 품질 검증 → 기존 모델 평가 → 발견 → 한계 |
| 분석·실증 연구 | 질문 → 실험 설계 → 발견 1 · 2 · 3 → 함의 |
| 서베이 | 범위 → 분류 체계 → 갈래별 정리 → 열린 문제 |

- 섹션은 읽는 순서대로 놓았을 때 단계가 **뒤로 돌아가지 않아야** 한다. 같은 단계의
  섹션은 붙어 있어야 한다 — 미니맵 레일이 앞으로만 채워지기 때문이다. 원문 순서가
  흐름과 어긋나면(예: §5 분석이 §4 실험보다 먼저 나옴) 단계 경계를 고친다. 섹션 순서는
  바꾸지 않는다.
- `summary` 는 그 단계에서 논문이 말하는 것 한 문장. 수치를 넣으면 앵커가 필요하므로
  Overview 흐름도에는 넣지 않는다.

## 3. 확인받을 초안의 형식

대화에 이렇게 보여 준다. 파일은 아직 만들지 않는다.

```
흐름: 문제 → 제안 방법 → 실험 → 결론 (4단계)

문제
  1    Introduction                         §1, p.1-2
제안 방법
  3    Model Architecture                   §3, p.2
  3.1  Encoder and Decoder Stacks           §3.1, p.3
  3.2  Attention  (3.2.1~3.2.3 합침)        §3.2, p.3-5
실험
  6    Results                              §6, p.8-9
결론
  7    Conclusion                           §7, p.10

뺀 것: §2 Background (Overview 에 한 문단), 부록 없음
페이지: Overview + 6장
```
