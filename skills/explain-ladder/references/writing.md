# writing — STE 원칙을 따른 글

ASD-STE100(Simplified Technical English)의 원칙을 **80% 정도** 적용한다.
목적은 검토자가 한 번 읽고 오해 없이 이해하는 것이다. 표준 준수가 목적이 아니다.

> 산출물에 "STE 준수", "ASD-STE100 표준에 맞춤" 같은 주장을 쓰지 않는다.

## 1. 문장 규칙

| 규칙 | 기준 |
|---|---|
| 한 문장에 한 내용 | 접속사로 두 동작을 잇지 않는다. 문장을 나눈다. |
| 절차 문장 길이 | 20단어 이내 (한국어는 어절 기준) |
| 설명 문장 길이 | 25단어 이내 |
| 능동태 | 주어가 동작을 한다. "~에 의해 ~된다"를 피한다. |
| 지시문 | 명령형. "~하면 됩니다" 대신 "~한다" / "~하세요" 중 문서 안에서 하나로 통일. |

나쁜 예: "토큰이 만료되었을 경우에는 refresh 로직에 의해 새 토큰이 발급되고 원래 요청이 재시도되는데 이때 실패하면 로그아웃된다."

좋은 예:
1. `validate_token` 이 만료를 감지한다.
2. `refresh_token` 이 새 토큰을 발급한다.
3. 클라이언트가 원래 요청을 다시 보낸다.
4. 재시도가 실패하면 `logout` 을 호출한다.

## 2. 용어 규칙

- 같은 개념에는 같은 용어만 쓴다. "세션"과 "로그인 상태"를 섞지 않는다.
- 처음 나오는 전문 용어는 한 번 정의한다. 형식: **용어**(정의 한 줄).
- 코드 심볼은 백틱으로 감싸고 원문 그대로 쓴다.

## 3. 한국어로 쓸 때

STE 의 어휘 규칙(승인 단어 목록, 단어당 한 의미)은 영어 전용이다. 한국어에는 **문장 구조 원칙만** 적용한다:
한 문장 한 내용, 길이 제한, 능동 서술, 용어 일관성.

## 4. 기본 구조 (개념 · 함수 · 결정 설명)

1. **한 줄 요약** — 무엇을 하는가 / 무엇을 정했는가.
2. **동작** 또는 **근거** — 번호 목록. 각 항목에 파일·심볼 근거.
3. **경계 조건** — 언제 다르게 동작하는가, 무엇을 하지 않는가.
4. **[확인된 사실] / [추론] / [불확실]** — SKILL.md 4.1.

## 5. 코드 변경 인계 형식

PR 정리, 리뷰어용 요약, 큰 작업 후 인계에 쓴다. 다섯 절을 이 순서로 둔다.

```markdown
## 변경 전 동작
- (사용자·호출자 관점에서 무엇이 일어났는가)

## 변경 후 동작
- (무엇이 달라졌는가. 달라지지 않은 것 중 오해하기 쉬운 것도 쓴다)

## 영향받는 파일·심볼
| 파일 | 심볼 | 변경 |
|---|---|---|
| `src/auth/session.py` | `validate_token` | 만료 여유 시간 30s 추가 |

## 테스트
- 실행함: `pytest tests/auth -q` — 42 passed
- 실행하지 않음: 통합 테스트(`tests/e2e`) — 스테이징 자격 증명이 없음

## 남은 리스크
- (검토자가 특히 볼 곳. 없으면 "확인된 리스크 없음"이라고 쓰고 그렇게 판단한 근거를 쓴다)
```

- "실행하지 않은 테스트"는 생략하지 않는다. 없으면 "없음"이라고 쓴다.
- 테스트 결과는 실제 출력에서 옮긴다. 실행하지 않은 결과를 통과로 쓰지 않는다.
- 인계 형식 뒤에도 [확인된 사실] / [추론] / [불확실]을 둔다.

## 6. 상위 포맷 제안

글을 쓰다가 아래 신호가 보이면 마지막 줄에 한 번 제안한다.

- 문단 안에 "A 가 B 를 부르고, B 가 C 를…"이 세 번 이상 이어진다 → diagram
- "값이 크면 ~, 작으면 ~" 식의 조건 비교가 세 개 이상이다 → html
